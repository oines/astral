# 图片准入与 Compact 恢复性能验证

## 最终实现与测量边界

最终受测 Core 为 `7ee9c79384eed7e462c8fe95c6d9b3340bc1459e`，合并提交 `4e2310bd0d4a8a673c18f5aa4f9323c6287f6515` 的文件与其完全一致，Host 固定该公开模块版本。Host 为 `cbcde40` 加本次产品修改；编译时 Go 产品差异 SHA256 为 `249ef87471d079a4e22ddafbe72695ff098131c7d28e893d9dbc75a4615d2edb`。源码、模块及二进制绑定在私有诊断目录保存，测试前后产品文件哈希一致。依赖固定后的新增模块是同一版本 VPX；没有通过本地 replace 发行。

本次保留三个简单改动：公共恢复边界隔离请求后，内部包装直接转发；小于 4 KiB 的未匹配请求尾部使用已有字面量记录，避免扫描全部历史；图片准入使用成熟的原生 Go VPX 编码器单次压缩。没有新增缓存、后台任务、存储格式、质量搜索或缩放重编码循环。

Core 仍是独立 SDK。默认 `CompressAboveBytes=150000`、`Quality=75`；Host 的 IM 预览传入 `30000`、`30`。字节数按 base64 计算，是**压缩触发阈值，不是输出上限**。默认保留原尺寸；只有调用方显式设置尺寸限制才缩放一次。满足阈值的小原件直接返回；无强制格式、朝向或尺寸纠正时，编码更大则保留原件。原有独立的 4.5 MiB 硬上限与解码像素保护继续生效。后续请求、Probe、Compact 和重放复用已冻结图片，不重写旧历史或原附件。

最终对照统一使用 Apple M2、Darwin arm64、Go 1.26.4，并通过同一文件锁串行运行。独立图片对照使用 CGO=0；Compact 和正常请求的诊断程序两边均使用 CGO=1，其中 Compact 的 Mach 内存采样器需要 CGo。编码依赖本身不要求 CGo。墙钟耗时、进程 CPU、累计分配、GC 后活跃堆和 RSS 分开记录；强制 GC 只用于计时外诊断。私有图片、聊天、数据库、API 密钥和模型识别原文均不提交到仓库或 GitHub。

## Compact：问题来源与修复证据

先前已合并的 Core 恢复修复 `58837cea5c1aa71225b45112a0d1b789e1167b1b`，移除了多层公共恢复入口中的 JSON 往返复制。本次 Host 包装器同步直接转发已隔离请求。早先 Go 1.26.3 的同输入三轮对照中，Compact 中位耗时从 1911.995 降至 619.138 ms，累计分配从 911.724 降至 397.488 MiB；这是第一阶段证据，不与下表混用测量批次。

剩余开销来自 `selectRequestMessages`：Compact 在历史后追加一条新的短摘要指令，引用选择器为了查找这条新消息，先对全历史构建 `canonicalDigest` 索引，执行 JSON 编码、解码、重编码与哈希，重复处理图片数据。

最终修复先检查**整个未匹配尾部**是否小于 4 KiB，若满足就使用既有字面量记录；较大或移位历史继续使用原索引。不是逐条把小消息复制到持久历史。前插、中插、删除的千条短消息测试中，Changes 正文小于 1 KiB 且不重复历史；Selection 索引仍随消息数增长。请求重建及 Digest 校验保持。

以下仅隔离这项索引修复：基线 Core `58837ce`，候选 `7ee9c79`，两边 Host 恢复包装均直接转发，各三轮。六次均重建相同请求摘要、选取 980 项、发送 36,178,535 字节、只调用一次离线 HTTP 413，失败后未消费输入保持。

| Compact 阶段，中位数 | 改前 | 最终版本 |
| --- | ---: | ---: |
| 墙钟耗时 | 610.040 ms | 181.449 ms |
| 进程 CPU 时间 | 631.762 ms | 188.319 ms |
| 累计分配 | 396.487 MiB | 112.775 MiB |
| 10 ms 采样及端点的峰值 RSS | 180.438 MiB | 165.891 MiB |
| 保留一个活动窗口，GC 后活跃堆 | 55.692 MiB | 55.530 MiB |
| 单独冷打开耗时 | 1511.214 ms | 1521.512 ms |

最终三次 Compact 为 178.428–183.627 ms。耗时降低约 70%，分配降低约 72%；活动上下文本体没有缩小，不能把分配降幅当成 RSS 降幅。冷打开包含另一个历史加载过程，本次没有优化。

分配 profile 将改前约 284.34 MB 采样累计分配精确归到 `byDigest[canonicalDigest(old)] = j` 的全历史索引行；改后该行不再出现，`canonicalDigest` 无匹配分配样本。三轮合并的 Compact CPU profile 中，原选择器及该摘要调用累计 0.83 秒，候选不再出现。profile 是采样归因，表中精确累计分配另取自 MemStats 差值。

此重放包含原事故的旧图片，不靠重新压缩输入获得收益；它也没有重建 Desktop 全部服务或完整复现线上约 969 MiB RSS 峰值。

## 实际图片准入：收益与取舍

两版完整调用实际 `Core.ProcessImage`，包含解码、朝向、编码、base64 与 JSON；IM 原样使用各版真实 Host helper。12 案、168 次调用，每案冷 1 次、热 3 次、连续 10 次并允许自然 GC，另在计时外检查 GC 后保留量。

| 场景 | 热运行 CPU，旧 → 新 | 连续 10 次平均分配，旧 → 新 | 进程峰值 RSS，旧 → 新 |
| --- | ---: | ---: | ---: |
| 照片及评论 read | 214.68 → 127.10 ms | 85.44 → 8.14 MiB | 246.78 → 54.67 MiB |
| 照片及评论 IM | 76.79 → 117.52 ms | 18.91 → 13.59 MiB | 62.62 → 45.45 MiB |
| 文字截图 read | 1.88 → 125.53 ms | 3.38 → 10.18 MiB | 19.91 → 114.31 MiB |
| 文字截图 IM | 55.30 → 120.22 ms | 24.36 → 18.36 MiB | 60.14 → 116.44 MiB |
| 透明图 read | 0.16 → 0.16 ms | 0.28 → 0.28 MiB | 15.23 → 15.28 MiB |
| 透明图 IM | 28.45 → 175.45 ms | 12.53 → 16.01 MiB | 43.34 → 76.16 MiB |

照片 read 的 base64 从 877,408 降到 143,800 字节，并从旧版缩至 921×2048 改为保留 1080×2400。文字截图 read 从原件直通的 769,036 字节压到 134,944 字节，保留 1756×1410，因此增加了一次约 125 ms CPU 的入站工作。

IM 原来把图片缩到 75k 像素，文字截图只有 305×244；最终保留 1756×1410，文字更可辨，但 CPU 和峰值内存也增加。照片与截图的实际 IM base64 为 103,104 / 100,372 字节，**不是固定 30 KB**。透明图编码更大后保留原 PNG，仍已发生一次编码；其连续平均分配高于旧版，不能只挑热运行低分配样本宣称全面改善。

连续测试可见自然 GC 回落，未见活跃堆随调用次数持续线性增长。一次 GC 后编码器池可能仍保留工作区，第二次 GC 后候选相对输入加载基线仅多 0.004–0.024 MiB。此短实验支持工作区可回收，不证明无限长期或并发场景绝无增长，也不说明 RSS 立即回落。没有为此加入强制 GC 或自建缓存。

## 真实模型验证

使用用户授权的同一截图，通过最终 Core 和实际 Models SDK 分别发送 read 与 IM 成品。四次调用均 HTTP 200、SDK 正常结束，线上图片字节与本地成品 SHA256 一致，均为 1756×1410 WebP。read 成品为 101,206 原始字节 / 134,944 base64 字节，IM 为 75,278 / 100,372。两条服务通道收到各自相同的图片成品。

| 服务与模型 | read 文字核对 | IM 文字核对 |
| --- | --- | --- |
| DeepSeek 官方，`deepseek-flash` | 完整匹配 | 完整匹配 |
| Command Code，`deepseek/deepseek-v4.1-flash` | 漏一个中文字 | 完整匹配 |

识字标准只忽略空白、外围引号和末尾句号。Command Code 的漏字不是格式差异，原失败布尔结果保留，没有更改规则或重试挑样本。SDK/WebP 兼容性与原尺寸传输通过，文字样例为 3/4 完整匹配，不能据此承诺 OCR 总是准确；同一 read 成品在官方接口匹配，也不能将网关一次漏字直接归因于压缩器。

此前一次旧凭据 HTTP 401、两次模型路由 HTTP 400 均保留，未算作视觉验证。随后按两家当前文档和实时目录确认模型及 Responses 路由，四次验证通过用户临时提供的 stdin 密钥完成，不读取或更改正式服务配置。网络和生成用时约 2.1–5.1 秒，不计入本地准备指标。原始图片、模型识别原文及凭据不随代码发布。
