替换程序时保留原来的数据目录。可用下载见[获取 Astral](/zh-cn/docs/start/get-astral/)；下面的流程适用于包含更新器和迁移工具的构建。旧的不带更新器版本需要先手动安装一次，之后才能在 App 内更新。

## 更新 Desktop

在 App 中，或登录其 Server 的网页后，打开 **设置 → 关于与诊断**。软件更新行只有一个按钮：没有新版时为**检查更新**，有新版时为**更新并重启**，失败后显示对应的重试动作。受支持的 Desktop 也会在启动后及运行期间定期检查版本信息。检查不会下载安装包。

点击**更新并重启**后，Astral 会重新检查最新版，下载并校验完整更新，再安装重启。网页操作会交给正在运行的 Desktop App 更新器，不会在 App 之外另装一个 Server。

| 安装方式 | 更新方法 |
| --- | --- |
| 官方签名的 macOS App | 在 App 或其已登录网页中点击**更新并重启** |
| 当前用户的 Windows EXE 安装版 | 在 App 或其已登录网页中点击**更新并重启** |
| Linux AppImage | 在 App 或其已登录网页中点击**更新并重启** |
| Linux DEB、Windows ZIP、未签名 Mac 或开发构建 | 手动下载安装新版 |

下载期间可以继续使用 Astral。下载完成后的安装会先停止本地 Server，中断正在运行的任务和电脑命令，因此请在可以接受中断时点击**更新并重启**。普通退出不会安装更新。检查失败时重试检查，更新失败时重试更新；检查更新不会开始下载或安装。本机电脑服务随 Desktop 更新，远程电脑需要单独执行更新操作。

网页可能在重启期间断线。它会等待 Server 恢复，并核对本次更新操作的结果和实际运行版本；仅仅失去连接不表示更新失败，也不需要再次提交。更新失败或恢复到原版本时，仍会显示失败，不能当作升级成功。

如果 Mac 发行说明标注 Apple 公证仍在等待，表示 Developer ID 签名已验证，但首次打开仍可能被 Gatekeeper 拦截。尝试打开可信的官方下载后，可按照 [Apple 的说明](https://support.apple.com/en-us/102445)，在 **系统设置 → 隐私与安全性 → 仍要打开** 中允许本次打开。这与 Astral 的 App 内更新功能是两回事。

## 更新无界面 Server

由官方 Linux 当前用户安装器管理、且安装信息通过验证的服务，可以在 **设置 → 关于与诊断** 使用同一更新按钮。先检查新版，再在可以中断任务时点击**更新并重启**，不需要浏览器访问终端。

独立、可见的一次性 systemd 用户任务会下载并校验选定的官方发行版，完成后才停止 Server 服务。安装根目录、数据和网络设置保留，新 Server 在启动时执行所需迁移。激活失败时，安装器先完成原程序、用户服务及本次数据快照的恢复，任务再记录失败结果。操作记录位于安装根的 `updates/`，在 Server 数据备份范围之外，不会因回退而丢失。重新连接并确认结果后，再恢复工作。

旧的官方安装若只显示手动下载入口，以同一账户、相同根目录重新执行一次[安装命令](/zh-cn/docs/hosting/server/)，即可准备当前安装信息与服务定义。这也是保留的命令行更新方式，可以显式指定已发布 Tag。仅设置安装根目录，不能替自定义服务取得自动更新权限。

前台 `serve`、自定义服务或自行部署的容器，继续按原部署方式更新：先停止进程、替换程序，再用原来的 `--data` 目录和启动参数重新启动。这些部署不承诺网页一键替换。独立 Server 的本机电脑服务随 Server 更新，不要因为更换可执行文件而意外使用空数据目录。

## 跳过版本与数据转换

只需要下载最新版应用。最新版包含所有受支持的历史数据迁移，并按顺序执行缺失步骤，不需要下载或安装中间版本的应用。

需要转换数据时，启动流程会先取得独占运行权并备份完整 Server 目录，在迁移和准备数据库期间保留恢复信息，随后在接受网页、API 或聊天工作之前确认升级。迁移或准备阶段失败会恢复该次备份，确认前中断则在下次启动时先恢复。确认后可能已经接受新工作，后续故障不会自动恢复旧数据。Linux 安装脚本若在本次激活检查中失败，会另行恢复本次升级的快照；Desktop 不会在每次启动失败时自动回退 App。自动快照位于 Server 数据目录同级的 `upgrade-backups/`。

首次公开发行支持的数据基线为 Host 3 / Core 11，当前目标为 Host 6 / Core 11。Desktop 从 0.1.0 或后续版本升级时继续使用原来的 `schema-3-core-11/` 目录，保留已有设置、历史和电脑身份。缺失迁移按顺序执行：步骤 4 恢复仍绑定 IM 却已归档会话的可见性，步骤 5 将已有会话初始化为非私密，步骤 6 统一已保存的出站消息内容并保留发送结果和幂等记录，同时恢复仅因私密初始化改变的会话原活动排序。此前会话版本、IM 事件和 Core 历史完整保留，普通归档会话不变。

更早的私有 Core 10 等数据不导入；旧的 `schema-3/` 等目录完整保留，不会转换或删除。显式指定更早的私有开发格式或未知的新格式时，启动会被拒绝。安装旧程序不等于数据降级：恢复旧数据需要匹配的备份和程序版本。请继续维护独立备份，包括电脑上的工作文件，不要只依赖升级快照。

## 开发版的存储维护

当前开发分支新增 Core SQLite schema 12，Core 逻辑格式保持 11，Desktop 数据目录也保持不变。这项存储升级尚未随正式版发布。自动迁移会共享重复的大段正文，并将输入和队列中的副本改为事件引用。消息、时间、历史中已有的附件内容和模型请求边界保留原有逻辑值，不重新获取媒体。

转换前，Astral 会检查完整备份、数据库转换、临时文件和恢复所需的空闲空间。最终数据库变小不代表升级过程不需要额外空间。如果预检失败，先释放空间，或在停止 Server 后把完整数据目录迁到合适的卷，再重试。已完成的升级备份会保留。

这个版本在启动数据维护持续超过 300ms 时显示准备窗口，并等待对应的 Server 进程完成维护；关闭窗口即可取消启动。转换被取消或中断后，下次启动会恢复。更新后的 Linux 安装器也会等待数据准备，不使用普通服务启动超时中断迁移。已经运行的旧安装器仍有原来的时间限制；通过旧入口升级大型数据库时，可先使用离线迁移命令。

### 查看与清理存储

在 Desktop 或其已登录网页中打开**设置 → 存储**。总览展示数据卷容量和 Astral 已识别文件的实际大小，包括数据库附属文件、升级备份、已识别缓存与临时文件。应用数据库同时保存 IM 归档、设置及其他应用记录，不只是配置。连接电脑上的工作文件单独保留。

总览下方选择 Bot，进入它的**聊天**和**其他会话**。每个聊天包含 IM 归档与当前绑定的 Astral 会话；以前解绑的旧会话保留在其他会话中。列表里的大小条是归档正文、会话记录、状态和模型调用历史的逻辑估算，不是各对象独占的磁盘空间，也不是删除后能释放的大小。共享正文、索引和数据库空闲页都会使逻辑估算与实际文件大小不同。可以按需刷新估算；部分结果或失败会保持明确标记。

清理聊天归档、设置归档保留期限和清理当前会话是不同操作。具体影响与其他会话永久删除的前提，见[管理会话与聊天存储](/zh-cn/docs/usage/conversations/#管理会话与聊天存储)。

**应用清理**只列出能确认属于当前 Server 的文件：可删除的升级备份、模型目录缓存和已识别的过期临时文件。安装版 Desktop 还会在更新器配置和下载元数据能够确认归属时，列出旧更新安装包；待安装的新版本、恢复所需的包以及下载或安装中的更新受到保护。未能确权的缓存不列出，独立 Server 也不会假装能够访问 Desktop 缓存。

选择条目后，确认**删除所选文件**。最近恢复点和正在升级、恢复时所需的快照受到保护；文件或恢复依赖已经变化时，需要刷新清单。这个入口不删除未知日志或电脑工作文件。

删除备份会永久移除这份恢复副本。以前的备份仍可能包含后来已被删除的历史；普通会话或归档清理不会改写备份。请按自己的恢复需要另行保留独立备份。

### 自动回收数据库空间

会话删除或清理后，Astral 会将磁盘回收请求加入后台队列，等待空闲时机。Desktop 管理的 Server 和前台运行的 `serve` 都可以在运行中完成，不需要用户自行停服。回收任务对 Core、应用数据库和已经存在的回忆索引库执行完整 VACUUM，并完成 WAL checkpoint，不增加 schema 迁移。

全量整理需要额外工作空间，期间存储请求可能等待。删除内容不保证文件立即变小；页面分别显示排队、等待、执行中和失败，数据库忙时稍后自动重试，其他失败可在处理原因后重试。回收失败不会撤销已完成的清理。维护后重新测量磁盘用量，不用删除记录的逻辑大小推算实际释放量。

### 离线维护 Core 数据库

命令行仍提供单独回收 Core 数据库空闲页的方式。运行前保留完整备份并停止 Desktop 或 Server：

```sh
astral maintenance vacuum --data /path/to/server
```

这是离线操作，会检查空间和数据库完整性，只处理 Core 数据库，报告其主文件前后的大小，并保留全部升级快照。回收数据库空闲页不等于删除备份，也不改变会话历史。其他程序正在使用这份 Server 数据目录时，不要运行该命令。

## 更新远程电脑或容器

打开 **设置 → 电脑 → 电脑详情 → Daemon 维护**。对于已在线、支持管理更新的电脑，点击**更新 Daemon**，并确认正在运行的任务会停止。Astral 会下载并校验官方版本、替换程序，再检查同一台电脑重新连接。如果 Daemon 比 Server 更新，Astral 会提醒更新 Desktop 或 Server，但不阻止继续检查 Daemon 更新。即使两端当前版本相同，该操作仍会检查最新发行版；目标版本相同或更旧时不重复安装。

也可以复制页面显示的更新命令；旧 Daemon 尚不支持管理更新，或该操作不可用时，使用这种方式：

- 裸机：在目标电脑执行 Shell 或 PowerShell 命令，更新当前用户的后台服务。
- 容器：在 Docker 宿主机执行命令。它会替换 Daemon 并重启同一个容器，保留身份、已安装工具、可写层与数据。

新容器的管理更新由容器内监督进程接管，替换程序并重启 Daemon，不重新创建环境。更新 Daemon 不改变基础镜像；更新失败会尝试恢复原程序，也可能重启原版本。恢复任务前，先确认页面结果和电脑连接状态。若发行版修改了监督进程本身，更新后重启一次原容器即可加载这些修改，无须重建环境。

预构建 Ubuntu 环境独立于应用发版。新建容器拉取当前 Astral 版本指定的镜像摘要，再单独放入 Daemon。应用更新不会在用户电脑上重建镜像，也不会重建已有容器；原镜像、可写层、已安装工具、数据卷和配对挂载保留。程序需要更新时，使用独立的 Daemon 更新操作。环境准备和持久化说明见[使用容器](/zh-cn/docs/computers/containers/)。

## 备份哪些内容

| 对象 | 需要保留的内容 |
| --- | --- |
| Server | 完整数据目录，包括数据库、`master.key`、`computer-identity/` 和配置 |
| 本机及远程电脑 | 电脑服务数据、Bot 工作目录和实际项目文件 |
| 容器 | 数据卷，以及需要保留的容器可写层或重建方法 |

只复制数据库不够：加密密钥用于读取已保存的凭据，电脑连接身份用于保留现有电脑对 Server 的信任。Server 迁移备份不会从连接的电脑复制工作文件，也不能撤销已经发生的外部操作。

最直接的一致备份方法是停止 Desktop 或 Server，再复制完整 Server 数据目录。运行中备份需要采用一致的 SQLite 备份方式，不能随手复制一个正在写入的数据库文件。

## 找到数据目录

优先查看启动日志、电脑详情与实际启动参数。独立运行时默认使用以下 Astral 根目录：

- macOS：`~/Library/Application Support/astral`
- Windows：`%APPDATA%\astral`
- Linux：`$XDG_CONFIG_HOME/astral`，通常为 `~/.config/astral`

Server 数据通常在根目录的 `server/`，本机电脑数据在 `computers/`。Desktop 使用操作系统应用数据目录中的 `astral/schema-3-core-11/`：macOS 和 Windows 对应上面的 Astral 位置，Linux 通常为 `~/.config/astral/schema-3-core-11/`。Linux VPS 安装脚本则使用安装根目录下的 `data/`。自定义路径和环境变量优先。

## 恢复后检查

恢复前先停止 Desktop 或 Server。使用与备份数据匹配的程序启动，确认历史、已保存的模型连接、电脑在线状态和聊天账号，再恢复任务。不要让两个 Server 进程同时写同一个数据目录。
